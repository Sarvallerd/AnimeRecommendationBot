# Named release live acceptance (ARB-034)

This is an optional historical live-service procedure. The standard automated stand is [level-1 acceptance](LEVEL1_ACCEPTANCE.md); its synthetic results do not count as the human UI observations required below. Unobserved live cases remain `PENDING`.

This is the private, opt-in procedure for the existing user service. Run it only after ARB-034 has merged and the required checks on integrated `master` are green. The ARB-033 `preparation-report.json` proves full-input offline compatibility against synthetic history; it does not prove production history or Telegram UI. The ARB-034 verifier is read-only. The coordinator performs each service transition and records observations. Missing access or UI observation remains `PENDING`.

Use the genuine existing Compose project and PostgreSQL volume. Retain the original immutable bundle, original bot image, original settings bytes, private credentials and database volume throughout. Never run the ARB-033 acceptance project's bot or put a real token in that project. One Telegram token has at most one poller. Local Docker and known local process inventory cannot exclude an unknown remote poller. Do not use `getUpdates` as a probe. A Telegram send and PostgreSQL write are not exactly once.

## Private preparation

Create a new ignored directory outside every worktree, owned by the service operator, with mode `0700`; create `captures`, `operations/inputs`, `results/inputs`, and `inputs` at mode `0700`. Keep every capture, plan, context, settings copy, observation, operation and case result private (`0600`). Never display a snapshot, token, profile, action key, feedback body or actor ID in a terminal, commit, PR or Notion. The public report is generated by an allowlist.

Set these variables to private absolute paths and the existing project. Use the integrated checkout and the same Docker daemon and settings on every command. A Docker wrapper, if needed, must preserve argv and bound execution. Check Docker access and recover the **same** PostgreSQL container/volume to healthy service before the baseline; do not create another project with the real token. Check that the original bot is healthy, has the original immutable bundle, and is the only matching local poller.

```bash
CHECKOUT=/absolute/integrated/checkout
PROJECT=existing-service-project
SETTINGS=/absolute/private/active-compose.env
OFFLINE=/absolute/private/accepted-arb033-evidence
TARGET=/absolute/private/retained-reference-A-bundle
UI_PROBES=/absolute/private/ui-probes.json
RUN=/absolute/private/new-live-run
EVIDENCE="$CHECKOUT/deploy/tests/acceptance-evidence.py"
compose() { docker compose --env-file "$SETTINGS" -p "$PROJECT" -f "$CHECKOUT/compose.yaml" "$@"; }
python3 "$EVIDENCE" live-v2 capture --project "$PROJECT" --settings "$SETTINGS" \
  --output "$RUN/baseline.json"
python3 "$EVIDENCE" live-v2 plan --project "$PROJECT" --settings "$SETTINGS" \
  --offline-evidence "$OFFLINE" --baseline "$RUN/baseline.json" \
  --target-bundle "$TARGET" --ui-probes "$UI_PROBES" --output "$RUN/plan.json"
```

The plan reopens the complete retained ARB-033 evidence and frozen inputs at their recorded absolute locations, checks the original against the historical bundle and target against reference A, and binds the offline report SHA, trusted profile/lock, current source/Compose/SQL/verifier, Docker daemon, PostgreSQL container/image/volume, settings metadata and credential fingerprints. B is an offline comparison build and cannot be the target. The plan creates private original/target settings copies by changing only `ARB_BUNDLE_DIR`; it does not change active settings. The UI probe file is schema 1, kind `arb-live-ui-probes`, with `alias_search:{mal_id,query}` and `description_edit:{seed_mal_id,query,neighbor_mal_id}`. Choose an actual target alias distinct from the primary title and a real target neighbor with a description. These probes establish catalog facts, not observed UI.

Do not start transitions if the baseline cannot prove one local matching poller, healthy PostgreSQL, exact original bundle, stable settings and credentials. Save the original bot image ID and target image ID from the private plan. The target project tag must resolve to the exact ARB-033 verified bot image ID; preserve a local tag for the original image. Do not rebuild an image and describe it as the verified ARB-033 image.

## Three recorded transitions

Run `initial-update` (original → target), `rollback` (target → original), then `final-update` (original → target). Each transition needs four new **full** captures in order: `before` with one old poller, `stopped` after stopping that bot with zero pollers, `prepared` after a fresh successful one-shot prepare with zero pollers, and `started` after a fresh new bot with one poller. Use `capture --plan "$RUN/plan.json"` and new output filenames for every capture. The capture checks settings and credential fingerprints, Docker daemon identity, PostgreSQL health and local poller inventory both before and after the read-only SQL snapshot. If inventory is incomplete, the verifier returns `POLLER_SCOPE_PENDING`; if the guards changed, it returns `UNSTABLE_CAPTURE`. Do not edit those facts into a PASS.

For each transition, stop only `bot` (`compose stop bot`), then capture `stopped`. Atomically install the plan's selected settings copy into the active settings path, preserving owner and mode, and tag the selected preserved image ID as this project's bot image. Run `compose up -d --no-deps --no-build --force-recreate prepare`; require exit code zero and the selected bundle identity. Capture `prepared`. Run `compose up -d --no-deps --no-build --force-recreate bot`; require its new container to load that identity. Capture `started`. The verifier checks old bot stop, fresh successful prepare after `stopped`, fresh bot start after prepare, exact image/UID/read-only mount/bundle identity/count, one→zero→zero→one pollers, unchanged healthy PostgreSQL container/image/volume and identical complete database rows and timestamps across the four captures. Do not delete the original bundle, volume or image. If a transition fails, preserve every receipt and restore from the saved original settings/image deliberately; start a new evidence run for another attempt.

```bash
python3 "$EVIDENCE" live-v2 verify-operation --plan "$RUN/plan.json" \
  --operation initial-update \
  --before "$RUN/captures/initial-before.json" \
  --stopped "$RUN/captures/initial-stopped.json" \
  --prepared "$RUN/captures/initial-prepared.json" \
  --started "$RUN/captures/initial-started.json" \
  --output "$RUN/operations/initial-update.json"
```

Repeat with `rollback` and `final-update` and their corresponding four captures. Keep the three operation results in `operations/`, and capture input copies in `operations/inputs`. The verifier recomputes them at summary time. Use fresh filenames; never overwrite a failed receipt.

## Actor and machine windows

After `initial-update.started`, one private-chat actor performs a new target smoke search and selection. Capture a full `after` immediately, before rating. `bind-actor` derives the actor from exactly one new resolved request, checks the target profile's smoke seed/query, exact ordered deliveries and private chat coordinates, and requires the anchor cards to be unrated. Ambiguous requests fail. The context is private; actor IDs are never CLI arguments or public output. Human confirmation of the interaction remains separately required.

```bash
python3 "$EVIDENCE" live-v2 bind-actor --plan "$RUN/plan.json" \
  --initial-operation "$RUN/operations/initial-update.json" \
  --after "$RUN/anchor-after.json" --output "$RUN/context.json"
python3 "$EVIDENCE" live-v2 verify --context "$RUN/context.json" \
  --case initial-update --operation "$RUN/operations/initial-update.json" \
  --before "$RUN/captures/initial-before.json" \
  --after "$RUN/anchor-after.json" --output "$RUN/results/initial-update.json"
```

Run each of the 21 machine cases once, with full before/after captures immediately around the action, using the same `verify` form and one new result in `results/`. `db-outage` also takes a `--during` runtime-only capture while only this project's PostgreSQL is stopped; restore the same container and volume before the full `after`. `rollback` and `final-update` require their operation result and a real new smoke flow after the new bot starts. `catalog-stale` requires the final-update operation and an unused original control from the verified rollback flow; the machine check establishes no database effect and target runtime. It cannot prove the human pressed the control. `description-edit` verifies the selected target neighbor and no new database effect; observe expansion/pages/collapse of the same text or caption card. The runtime does not promise a delete workflow. Idempotent editing does not prove a particular Telegram transport error.

The remaining cases retain their v1 action meanings, with profile-derived target seeds, order and counts: recommendation scores/repeat, empty, anime scores 1/10/repeat, Unicode feedback, navigation search/choice/anime-score/feedback, restart, database outage, feedback retry/repeat. `alias-search` uses the pinned real alias. `empty` may be `NOT_APPLICABLE` only when the accepted target profile has `empty_seed:null` **and** the actual target has zero empty lists; this release has a real empty case. Historical rows with unknown bundle identities remain valid. A concurrent unrelated write makes the measured window unsuitable; preserve it and take a new window, never delete it for PASS.

## UI observations and summary

Store schema 2 kind `arb-live-observations` with `plan_sha256`, `context_sha256`, and exactly one `scenarios` entry for each of: `actor-confirmation`, `search-selection`, `alias-search`, `card-content-and-order`, `description-edit`, `score-ranges`, `confirmations`, `empty-notice`, `consumed-controls`, `catalog-stale-controls`, `restart`, `outage-failure`, `retry-success`, `initial-update`, `rollback`, `final-update`, and `navigation`. Each entry has `id`, `status` (`PENDING`, `PASS`, `FAIL`, or the narrowly allowed `NOT_APPLICABLE`), UTC `observed_at` for PASS, a non-identifying observation of at most 240 characters, and `case_sha256` references to verified case results. Record only actual independent human observations. The only allowed UI `NOT_APPLICABLE` is empty notice when machine empty is legitimately not applicable. A machine no-effect result never becomes a UI PASS by itself.

Capture one final full target state after all cases. Then recompute saved operation and case inputs, history from baseline to final, current target selection and UI status:

```bash
python3 "$EVIDENCE" live-v2 summarize --plan "$RUN/plan.json" \
  --operations-dir "$RUN/operations" --results-dir "$RUN/results" \
  --final "$RUN/final.json" --context "$RUN/context.json" \
  --observations "$RUN/ui-observations.json" \
  --output "$RUN/private-summary.json" --public-output "$RUN/public-summary.json"
```

Without context or observations, omit those arguments and the live result stays `PENDING`. The public JSON contains only allowlisted statuses, aggregate counts, bundle identity, capture time and scope limits. It is a report of the captured interval, not a claim about later service state. Keep the selected target bundle and PostgreSQL volume, and retain the original bundle/image/settings for rollback.
