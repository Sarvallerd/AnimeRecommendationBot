# Russian private-chat dialogue

The runtime validates the generated bundle, builds an immutable Unicode title index, connects to PostgreSQL, then starts `bot::handlers::schema()` with an `AppContext`. Sessions are held per `(chat ID, user ID)` behind an async lock. Restarting the process clears state and all callback tokens.

All six commands work in every state. `/start` clears the session, upserts the actual Telegram profile, and shows the Russian menu. `/help` leaves state unchanged. `/cancel` closes the current dialogue. A pending feedback operation remains available through `/feedback`. `/recommend` and `/rate` prompt for a title. Search also upserts the actual sender profile, so either flow works without `/start` and after a failed start registration. `/feedback` prompts for one text message and also works without `/start`. Group commands direct users to private chat; ordinary group messages are ignored.

Search accepts up to 256 Unicode scalar values and rejects NUL and blank normalized text. It applies NFKC, lowercase conversion, and punctuation/space collapsing to canonical titles and provided aliases. It does not transliterate or add Russian aliases. Exact, prefix, substring, and bounded typo matches rank in that order; ties use distance, excess title length, then numeric MAL ID. Queries shorter than three normalized characters match only exact titles. Five distinct IDs are shown at most, including separate IDs with the same title. The user sees numbered canonical titles, year/type when present, and MAL IDs, and must confirm a button even for one exact match. Display text is bounded by UTF-16 units; database and index text are not truncated.

A valid query first replaces old search state and buttons with `PendingQuery`. The bot upserts the sender profile and calls `record_query` with the exact raw message text and `msg:<chat_id>:<message_id>`. A successful candidate keyboard moves the session to `ChoosingAnime`. An uncertain database write or failed candidate send keeps the pending payload and offers an opaque retry button. Retrying uses the original message key and text. Failed retry claims remain available and do not accumulate buttons. A no-match query is still recorded, and a successful notice returns to the title prompt. A fresh query invalidates old candidate buttons. A duplicate source message while choosing preserves the current buttons and selected ID; changed text with that same source key is rejected.

Callback data is a random 128-bit token in `a1:` plus 32 lowercase hex digits. The server binds each action to its session owner, generation, state, originating bot message, and stable callback action key. Tokens activate only after Telegram confirms the keyboard message. Each callback is acknowledged before session or database work. A claimed token cannot run concurrently; a failed operation can be retried. The server never decodes an ID or score from callback text.

The central router pins the first valid candidate ID in `ChoosingAnime` before calling `resolve_request` with the loaded bundle identity. A different candidate cannot replace the pin, including after uncertain database results or a failed feature send. The same button can retry. `ResolvedSelection.query` carries the original query text, message action key, and stable request ID to the later recommendation and rating handlers. Those handlers should preserve the resolved request and callback generation when resuming retries. Database conflict or missing/invalid request resets the selection with a new-query instruction. Telegram send outcomes can be ambiguous, so a retry may repeat a message; delivery handlers must persist only confirmed sends and use stored delivery positions to avoid known duplicates.

The shared integration points are `search::{begin,on_message,on_retry,on_select}`, `handlers::ui::send_keyboard`, `recommendations::begin`, `ratings::{begin,on_score}`, and `feedback::{begin,on_message,on_retry}`. `Action::RecommendationScore` reaches `recommendations::on_score` only after the router checks its delivered position against the owned request and chat. Transport errors are logged by the dispatcher using fixed text so they cannot disclose a bot token.

Feedback uses the exact original message body and `msg:<chat_id>:<message_id>` key. The bot saves the actual sender profile before writing the feedback row. Empty or NUL-containing text and nontext messages are rejected. A failed database write keeps the original message available through a retry button. If the row was confirmed but the Telegram notice failed, retry sends only the confirmation and does not contact the repository again. `/feedback` can reopen the original operation after another command or a failed retry prompt. A repeated original update in another dialogue is ignored; changed text under its message key is rejected. Restart clears the pending operation and buttons, while committed rows remain in PostgreSQL.
