# Russian private-chat dialogue foundation

The runtime loads and validates the recommendation bundle, connects to PostgreSQL, then starts the public `bot::handlers::schema()` router with an `AppContext`. Its repository trait mirrors the typed v1 database operations and accepts fake implementations for handler tests. State is held per `(chat ID, user ID)` in memory; each session has its own async lock. Restarting the process clears every state and button token.

All six commands work in every state: `/start` resets the session, upserts the user's profile, and shows a Russian menu; `/help` lists commands without changing state; `/cancel` clears the session; `/recommend` and `/rate` begin a fresh title prompt; `/feedback` is a visible placeholder until ARB-017. Search, recommendation delivery, and scoring are also visible placeholders until their respective tasks. They do not report results or saved data. Commands in groups direct users to private chat; ordinary group messages are ignored.

Callback data is a random 128-bit token in `a1:` plus 32 lowercase hex digits. Tests can inject a deterministic token source through `SessionStore::with_token_source`. The server binds its action to the session owner, generation, state, originating bot message, and stable action key. Tokens activate only after Telegram confirms the keyboard message. Each callback is acknowledged before session or database work. Invalid accessible private callbacks get a stale-button notice. A claimed token cannot run concurrently; a failed operation can be retried with its original key. The handler never decodes IDs or scores from callback text.

The integration points for follow-on tasks are `search::{begin,on_message,on_select}`, `recommendations::begin`, `ratings::{begin,on_score}`, and `feedback::{begin,on_message}`. Search must call `record_query` using `msg:<chat_id>:<message_id>`, then write candidates to `State::ChoosingAnime` and issue selection buttons through the session. The selection handler calls `resolve_request` with the loaded bundle identity before constructing `ResolvedSelection`. Delivery writes follow confirmed Telegram sends. A database failure after a possible commit must say only that confirmation failed; an explicit retry uses the same action key. `Action::RecommendationScore` is dispatched through `recommendations::on_score` after the central router checks the position against `list_delivered_positions` for the owned request and chat. ARB-016 owns that module entrypoint. Scores and feedback must use the typed repository methods and their documented ranges. Dispatcher and polling errors log only fixed failure messages so transport errors cannot disclose a bot token.
