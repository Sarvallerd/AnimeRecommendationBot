# Recommendation delivery

After a user confirms an anime, the bot reads that seed's canonical neighbors from the loaded bundle. It sends one Russian card for each neighbor, in bundle order, with ranks 1–5: a photo with caption when a cover URL is available, or a text message otherwise. Cards show the seed and recommendation titles, MAL ID and score, year, type, episode count, genres, and a synopsis preview. The seed uses the spelling matched for the selected MAL ID by the original query, with the canonical title as fallback. If that spelling matches the seed's preferred Latin title under search normalization, neighbors use their preferred Latin titles: the first alias when it has an ASCII letter and no non-ASCII alphabetic letters after NFKD, otherwise the canonical title. Later aliases are not considered. Otherwise neighbors use canonical titles. This is a display heuristic; a Latin-only canonical title may be romaji. Missing metadata says `нет данных`; a missing synopsis says `Описание отсутствует.` Text cards retain the 160/240 UTF-16 seed/title bounds and 4000-unit message limit. Photo captions use a compact header, 64/120-unit seed/title bounds, and a 1024-unit limit. An empty neighbor list gets a single notice and no delivery row.

The bot records a delivery only after Telegram confirms the send, including an actual photo for media cards. Each row retains the original user request, seed, bundle identity, rank, recommended MAL ID, chat ID, message ID, and database insertion time. The card's text/photo format is kept in the current in-memory session for later edits; it is not persisted in PostgreSQL. A retry first reconciles any confirmed send awaiting a database write, then lists durable positions and sends only missing ranks. Conflicting history or a recorded position with unknown format stops delivery instead of guessing or looking up another cover. The pending coordinates and format stay in the in-memory session across `/cancel`, `/start`, and new searches; a new recommendation reconciles the old request before sending its own cards.

A confirmed Telegram response followed by a database failure keeps the original coordinates for retry. This protection lasts while the process lives. A process crash between Telegram and the database can lose those coordinates, and an ambiguous Telegram transport error can produce a duplicate message on retry. The database insertion timestamp may be later than the Telegram send. The `DeliveredPosition.id` is the stable identity for later recommendation feedback; rating controls must be attached only after its delivery row is durable.

## Recommendation usefulness scores

Each durable card gets six inline buttons labeled 0–5. The card explains that 0 means not useful and 5 means very useful. The bot attaches the buttons by editing the original Telegram message only after the delivery row has been saved. If that edit fails, a retry edits the same card with fresh opaque buttons; it does not send the card again. A pending delivery from an older request is saved under its original request, without adding buttons in a new selection.

The first score attempted for a position pins that value. If the database result is uncertain or the confirmation message fails, the same button can be pressed again. A successful retry confirms the existing immutable score. Other recommendation cards can still be scored independently. Once a score is accepted, the other visible numbers on that card are stale.

The usefulness confirmation uses the same neighbor-title preference as its card. If the target is unavailable, it says `Аниме`; if the seed is unavailable, it uses the target's canonical title.

The initial description shows up to three sentences, counting an unpunctuated ending as a sentence. Sentence boundaries use a small abbreviation and initial heuristic; unusual punctuation can still produce an imperfect preview. A long sentence is clipped to the text-message or photo-caption limit and remains expandable. `Развернуть описание` edits the same message's text or caption to numbered pages of the complete original synopsis. Expanded photo pages use a compact rank/title/MAL ID header to leave room for content. Page text is split on Unicode scalar boundaries and prefers whitespace; joining page payloads reproduces the source exactly. `Назад`, `Далее`, and `Свернуть описание` are repeatable read-only callbacks. They validate the current selection, owner, recorded position, and message before editing. A failed or ambiguous edit can be retried with the same button. The score row and its original tokens remain attached across page changes; an attempted score never regains discarded alternatives. Missing or short descriptions have no expansion button.

If `COVERS_ENABLED=true` (the default), shared Jikan and AniList clients look up each new card by positive MAL ID. Jikan uses `https://api.jikan.moe/v4/anime/{id}`; any miss or failure falls back to an AniList GraphQL lookup by `idMal` at `https://graphql.anilist.co`. Responses must contain the exact MAL ID and an HTTPS image URL on the provider's CDN (`cdn.myanimelist.net` or `s4.anilist.co`). A cached positive URL from either provider takes precedence over another lookup, so a working AniList cover remains available after Jikan's cooldown expires. The providers have independent gates and caches: Jikan request starts are at least 1100 ms apart with up to 1.2 seconds to acquire the gate and finish pacing; AniList starts are at least 2100 ms apart with up to 2.3 seconds for that wait. Only after the wait does the independent HTTP/body timeout begin: 1.4 seconds for Jikan and 2 seconds for AniList. Each cache holds up to 1024 entries: successful URLs last 24 hours, missing images and 404s last 10 minutes. Transient failures trigger a 30-second provider cooldown; HTTP or GraphQL 429 uses at least 60 seconds and honors longer valid `Retry-After` and AniList reset headers, capped at one year. GraphQL 404 is cached as missing; mixed or unknown GraphQL errors are transient, and errors take precedence over partial data. Positive cache entries remain usable during cooldown. Before a request starts, an expired waiting slot causes no cooldown. The bot sends a photo with its caption as the original card, with a 5-second Telegram photo timeout and no score keyboard until the message ID is durable. An absent cover produces a text card. Only four explicit Telegram media-rejection errors permit immediate fallback to a text card; timeout, network failure, rate limit, unknown API error, or an invalid photo response stops delivery for an explicit retry. An ambiguous photo send can yield a duplicate on retry. Retried recorded cards and reconciled older sends are not sent again. The caches are lost on restart; image availability depends on the providers and Telegram fetching the CDN URL. Provider and photo diagnostics contain only a fixed stage and reason, optional provider or HTTP status, and duration, without IDs, URLs, response bodies, or tokens.

If a later card fails during delivery, earlier cards and their buttons remain in place. Scores cannot be submitted until the selected recommendation flow completes on retry. Navigation and process restarts invalidate old buttons; stored deliveries and scores remain. A Telegram response lost after the database write can cause a duplicate confirmation on retry, while the database keeps one score per position.
