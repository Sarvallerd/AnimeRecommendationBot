# Recommendation delivery

After a user confirms an anime, the bot reads that seed's canonical neighbors from the loaded bundle. It sends one plain Russian card for each neighbor, in bundle order, with ranks 1–5. Cards show the seed and recommendation titles, MAL ID and score, year, type, episode count, genres, and a synopsis preview. The seed uses the spelling matched for the selected MAL ID by the original query, with the canonical title as fallback. If that spelling matches the seed's preferred Latin title under search normalization, neighbors use their preferred Latin titles: the first alias when it has an ASCII letter and no non-ASCII alphabetic letters after NFKD, otherwise the canonical title. Later aliases are not considered. Otherwise neighbors use canonical titles. This is a display heuristic; a Latin-only canonical title may be romaji. Missing metadata says `нет данных`; a missing synopsis says `Описание отсутствует.` The seed and neighbor titles are bounded to 160 and 240 UTF-16 units respectively, and each card is capped at 4000 UTF-16 units. An empty neighbor list gets a single notice and no delivery row.

The bot records a delivery only after Telegram confirms the send. Each row retains the original user request, seed, bundle identity, rank, recommended MAL ID, chat ID, message ID, and database insertion time. A retry first reconciles any confirmed send awaiting a database write, then lists durable positions and sends only missing ranks. Conflicting history stops delivery. The pending coordinates stay in the in-memory session across `/cancel`, `/start`, and new searches; a new recommendation reconciles the old request before sending its own cards.

A confirmed Telegram response followed by a database failure keeps the original coordinates for retry. This protection lasts while the process lives. A process crash between Telegram and the database can lose those coordinates, and an ambiguous Telegram transport error can produce a duplicate message on retry. The database insertion timestamp may be later than the Telegram send. The `DeliveredPosition.id` is the stable identity for later recommendation feedback; rating controls must be attached only after its delivery row is durable.

## Recommendation usefulness scores

Each durable card gets six inline buttons labeled 0–5. The card explains that 0 means not useful and 5 means very useful. The bot attaches the buttons by editing the original Telegram message only after the delivery row has been saved. If that edit fails, a retry edits the same card with fresh opaque buttons; it does not send the card again. A pending delivery from an older request is saved under its original request, without adding buttons in a new selection.

The first score attempted for a position pins that value. If the database result is uncertain or the confirmation message fails, the same button can be pressed again. A successful retry confirms the existing immutable score. Other recommendation cards can still be scored independently. Once a score is accepted, the other visible numbers on that card are stale.

The usefulness confirmation uses the same neighbor-title preference as its card. If the target is unavailable, it says `Аниме`; if the seed is unavailable, it uses the target's canonical title.

The initial description shows up to three sentences, counting an unpunctuated ending as a sentence. Sentence boundaries use a small abbreviation and initial heuristic; unusual punctuation can still produce an imperfect preview. A long sentence is clipped to keep the card within 4000 UTF-16 units. `Развернуть описание` replaces the same text card with numbered pages of the complete original synopsis. Page text is split on Unicode scalar boundaries and prefers whitespace; joining page payloads reproduces the source exactly. `Назад`, `Далее`, and `Свернуть описание` are repeatable read-only callbacks. They validate the current selection, owner, recorded position, and message before editing. A failed or ambiguous edit can be retried with the same button. The score row and its original tokens remain attached across page changes; an attempted score never regains discarded alternatives. Missing or short descriptions have no expansion button.

If `COVERS_ENABLED=true` (the default), a single shared Jikan client looks up each new card by positive MAL ID at `https://api.jikan.moe/v4/anime/{id}`. It accepts only the matching response ID and an HTTPS image URL on `cdn.myanimelist.net`. Requests start at least 1100 ms apart. Successful URLs stay in an in-memory 1024-entry cache for 24 hours, missing images and 404s for 10 minutes, and transient failures trigger a 30-second global cooldown; HTTP 429 uses at least 60 seconds and honors a longer `Retry-After` up to one year. A lookup is bounded to 1.5 seconds and the combined lookup/photo step to 2 seconds. The bot sends a silent, captionless photo replying to the durable text card after its score buttons are attached. Failed or absent images leave the text card usable; a Telegram photo failure skips further photos in that delivery call. Retried recorded cards and reconciled older sends do not get another photo. The cache is lost on restart; image availability depends on Jikan and Telegram fetching the CDN URL.

If a later card fails during delivery, earlier cards and their buttons remain in place. Scores cannot be submitted until the selected recommendation flow completes on retry. Navigation and process restarts invalidate old buttons; stored deliveries and scores remain. A Telegram response lost after the database write can cause a duplicate confirmation on retry, while the database keeps one score per position.
